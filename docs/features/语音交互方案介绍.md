# 级联语音 Agent 方案介绍

> 面向对象：产品、业务和管理人员  
> 首版定位：手机端实时语音对话，并完成微搜资料查询  
> 当前边界：先打通可靠主链路，多智能体和复杂办公操作后续逐步开放

## 1. 一句话说明

用户在手机上直接说话，系统把语音实时转成文字，交给现有 `VoiceAgent` 理解和执行；需要资料时调用微搜，得到结果后再转成自然语音播放给用户。

是基于现有 qll_chat Agent、工具权限和业务数据能力之外增加一条实时语音入口。

## 2. 用户会感受到什么

### 普通对话

1. 用户按下语音入口并开始说话。
2. 手机持续把声音发送给语音服务。
3. 系统判断用户是否开始、暂停或结束说话。
4. 语音被转换成文字，VoiceAgent 生成回答。
5. 回答一边生成、一边转成语音播放，不必等待整段答案全部完成。

### 查询资料

1. 用户说：“帮我查询某项资料。”
2. VoiceAgent 判断需要查询，只能调用首版开放的微搜查询和正文读取工具。
3. 手机端可以显示“正在查询”，但不会展示内部推理或工具参数。
4. 查询完成后，VoiceAgent 整理结果，再通过语音告诉用户。

### 用户插话

如果系统正在播报，用户可以直接再次开口。系统会停止旧回答、清空尚未播放的音频，并以用户的新问题开始下一轮。旧话轮即使稍后返回数据，也会被丢弃，不会重新播放。

## 3. 从用户输入到最终输出

```text
手机前端
  录音、播放、显示“聆听/思考/查询/播报”状态
      │ WebRTC 实时音频
      ▼
业务后端
  校验登录用户，创建可信会话，只向手机返回短期语音令牌
      │
      ▼
语音算法服务
  VAD 判断说话起止
      → ASR 把语音转成文字
      → VoiceAgent 理解问题并决定是否使用工具
      → TTS 把回答转成语音
      │ WebRTC 下行音频
      ▼
手机前端
  播放回答，继续等待下一轮
```

## 4. 整体输入输出对应关系

| 环节 | 输入 | 输出 | 输出去向 |
|---|---|---|---|
| 手机前端 | 用户说话 | WebRTC 上行音频 | 语音算法服务 |
| 业务后端 | 已登录用户和业务权限 | 短期语音令牌、会话地址 | 手机前端 |
| VAD / ASR | 实时音频 | 最终转写文本 | VoiceAgent |
| VoiceAgent | 转写文本、历史对话、可信用户上下文 | 普通回答，或微搜工具调用 | TTS 或微搜 |
| 微搜 | 查询条件 | 只读资料结果 | VoiceAgent 汇总 |
| TTS | VoiceAgent 的增量文本 | WebRTC 下行音频 | 手机前端播放 |
| 状态通道 | 当前会话和话轮状态 | 聆听、思考、查询、打断、完成等事件 | 手机前端展示 |



## 5. 三方职责

| 模块   | 主要职责                                          | 首版不承担的工作 |
|------|-----------------------------------------------|---|
| 手机前端 | 麦克风采集、WebRTC 连接、音频播放、状态展示                     | 不直接决定 Agent 权限 |
| 后端服务 | 待定                                            | 不处理 VAD、ASR、TTS 算法细节 |
| 算法服务 | WebRTC 音频接入、VAD、ASR、VoiceAgent 编排、TTS、插话和资源回收 | 首版不执行写操作，不运行异步多智能体任务 |

## 6. 为什么采用级联架构

级联架构把能力拆成“听见、转写、理解与执行、播报”四个可独立替换的模块。这样做的主要价值是：

- 复用现有 `/chat`、BaseToolAgent、微搜工具、权限和日志体系，减少重复建设。
- 每个环节可以单独定位故障，识别错误、Agent 错误和播报错误不会混在一起。
- 工具权限由服务端控制，首版只允许只读微搜，不会因为语音入口扩大业务权限。
- 后续可以分别升级 ASR、LLM 或 TTS，不必推翻整条链路。

缺点是链路环节较多，需要分别关注识别延迟、Agent 首字延迟、TTS 首包延迟和网络质量。首版必须通过真实手机和真实 API 联调建立基线。

## 7. 首版验收标准

1. 手机连续完成至少 10 轮普通话对话。
2. 至少成功完成一次微搜查询并播报结果。
3. 播报过程中插话，旧声音立即停止且不会恢复。
4. Wi-Fi 和移动网络都能建立连接，必要时使用 TURN。
5. 扬声器播放不会持续误触发麦克风，形成自问自答。
6. 失败能定位到 WebRTC、VAD、ASR、Agent、工具或 TTS 中的具体环节。

## 8. 未来扩展路线

### 第二阶段：扩大只读能力

逐项增加知识库、更多资料源、结果卡片和引用展示，每增加一种能力都单独验证权限、延迟和失败处理。

### 第三阶段：办公操作

增加创建日程、生成文档、发送消息等写操作。写操作必须加入用户确认、权限校验、审计和失败补偿，不能直接沿用只读查询策略。

### 第四阶段：异步多智能体

主语音对话继续陪伴用户，子智能体在后台执行较慢的查询或办公任务，完成后把结果交回 VoiceAgent，在合适的话轮统一播报。该阶段需要解决任务归属、取消、结果过期、唯一终态和恢复机制。


## 9. 结论

该方案的核心优势是：复用已有 Agent 和业务能力，同时把实时语音、插话、工具权限和安全边界独立控制。
