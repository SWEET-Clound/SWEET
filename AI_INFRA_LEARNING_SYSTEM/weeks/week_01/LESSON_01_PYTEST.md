# 巩固课 01：从“测试通过”到“知道测试证明了什么”

> 被测文件：`practice/test_grade_detect.py`  
> 实际结果：`1 passed in 0.03s`  
> pytest：9.1.1

## 1. 我们刚刚验证了什么

pytest 能找到名为 `test_grade_detect` 的函数并执行，其中所有 assert 当前都通过。

这证明：

- 项目虚拟环境可以运行 pytest；
- 当前列出的 90、60、100、0、-5 输入得到测试中写出的结果；
- pytest 遇到不满足的 assert 会把测试标记为失败。

它没有证明：

- 所有整数输入都正确；
- 101、91、61、59、负数的业务规则合理；
- 字符串、浮点数等错误类型得到清晰处理；
- 这个函数的等级规则符合真实需求；
- Agent 或项目其他部分正确。

核心思想：**测试证明的范围，永远不会超过你实际设计的输入和断言。**

## 2. 当前测试中值得观察的五件事

### 2.1 pytest 只报告了 1 个测试

虽然函数里有 6 个 assert，但 pytest 收集的是一个 `test_grade_detect` 函数，所以输出 `1 passed`。

如果中间某个 assert 失败，后面的 assert 不再执行。这也是参数化测试更适合边界表的原因之一。

### 2.2 `grade_detect(0)` 重复了两次

重复断言没有增加新的行为证据。它提醒我们：测试数量不是目标，覆盖不同风险才是目标。

### 2.3 无效输入依赖“隐式返回 None”

函数没有为 `-5` 写明确分支，Python 走到函数末尾后自动返回 `None`。测试虽然通过，但这并不等于设计明确。

需要先决定契约：

- 无效分数应该返回 `None`？
- 还是应该抛出 `ValueError`？
- 101 和负数是否属于同一类错误？

没有需求契约时，测试只能把偶然行为固定下来。

### 2.4 边界值比随机值重要

分支发生在 0、60、90、100 附近，因此至少要思考：

```text
-1, 0, 1
59, 60, 61
89, 90, 91
99, 100, 101
```

这叫边界值分析。错误最容易出现在 `>`、`>=`、`<`、`<=` 的交界处。

### 2.5 测试文件同时包含生产代码

当前适合做入门练习，但长期更清晰的结构通常是：

```text
practice/grade_detect.py
practice/test_grade_detect.py
```

这样测试导入被测模块，能够更接近真实项目结构。本次先理解原因，不要求立刻拆分。

## 3. 你的练习：先写行为表，不急着改代码

请根据你认为合理的规则填写：

| 输入 | 期望结果 | 为什么 |
| ---: | --- | --- |
| -1 | | |
| 0 | | |
| 59 | | |
| 60 | | |
| 61 | | |
| 89 | | |
| 90 | | |
| 91 | | |
| 100 | | |
| 101 | | |

然后回答：

1. A、B、C 的闭区间分别是什么？
2. 无效分数应该返回 `None` 还是抛异常？为什么？
3. `90` 为什么属于 B，而 `91` 属于 A？这是你真正想要的规则吗？
4. 测试里重复的 `grade_detect(0)` 应该保留吗？
5. 如果一次 assert 失败，当前测试函数后面的 assert 会不会继续执行？

## 4. 下一次实践目标

在你先确定业务规则后，我们一起把行为表变成 `pytest.mark.parametrize` 测试，并做一次完整的：

```text
先写失败测试（Red）
→ 修改实现（Green）
→ 整理重复和命名（Refactor）
```

这一步的目标不是学习装饰器语法，而是体会“需求契约先于实现”。

## 5. 掌握标准

达到 E2：

- 能解释为什么当前只显示 `1 passed`；
- 能说出测试证明和没证明的范围；
- 能找出重复断言；
- 能列出关键边界值。

达到 E3：

- 能先写清业务契约；
- 能用参数化表达行为表；
- 能让一个新测试先失败，再正确修改实现；
- 能解释为什么选择异常或 `None`。
